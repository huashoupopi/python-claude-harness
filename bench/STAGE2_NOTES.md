# mini-bench stage-2 归因笔记

**跑期**：2026-08-15
**被测**：`examples/22_trunk.py`（九件共存的主干，工具池 27 个）
**模型**：`grok-composer-2.5-fast`
**规模**：5 臂 × 8 题 × 3 trial = 120 单元，并行 4 路，`timeout=900s`

---

## 🔴 零、先读这一条：与 stage-1 的数据【不可比】

三处基线都变了，**任何把两阶段数字并排看的做法都会得出错误结论**：

| | stage-1（2026-08-11） | stage-2（2026-08-15） |
|---|---|---|
| 被测对象 | 四个**散件**（03/09/10/11） | 一个**主干**（九件共存，schema 11K） |
| 模型 | `deepseek-v4-flash` | **`grok-composer-2.5-fast`**（有 reasoning tokens） |
| 题库 | 3 道单点题 | 8 道，分 L1 单点 / L2 多点两层 |
| 判分 | 布尔（退出码） | 通过率 + 防作弊（判分前恢复原卷测试） |
| 成本口径 | 只有 steps | steps + **真实 token**（主循环/附加层分记） |

**换模型这一条尤其致命**：stage-1 的招牌结论「模型极少使用 `todo_write`」在新模型上**直接被推翻**——新模型无人催促就主动列计划（详见 §四）。

## 一、结论：todo 层是最大的成本项，且成本来自「工具的存在」

```
配置              steps    token    todo调用   改动行
todo_none          5.4    20.5k      0.0       9.8    ← 最省
mem_self(=nudge)  10.0    25.8k      2.1      11.2
mem_none          11.0    26.1k      2.4      10.8
todo_tool         11.0    27.6k      2.7      11.6
mem_official      11.6    29.7k      2.6      12.5    ← 最贵
```

配对比较（同题同 trial，只剩「配置」一个变量在动）：

```
工具本身   todo_none → todo_tool    5.4 → 11.0   +104%   配对 23:0   p<0.0001
系统催     todo_tool → todo_nudge  11.0 → 10.0    −9%    配对  4:12  p=0.038
```

> ### **可引用句：关掉 todo 工具，步数减半、token 少 26%，24 次配对里 24 次同向。而拆开看，成本几乎全在「工具存在」本身——系统每三轮催一次那个机制，反而让步数略降。**

**这是 stage-1 分不清、stage-2 才劈开的一刀**。stage-1 只能说「`todo_write` 是负担」；三档开关（`none` / `tool` / `nudge`）把「工具本身」与「系统主动催」分离，才知道该砍哪一半。

📌 **设计含义**：要省，砍的是**工具进不进池子**，不是**提醒机制**。而 `todo_write` 的 schema 是 947 字符——27 个工具的 schema 合计 11K 字符 ≈ 每轮固定开销，砍一个工具省的是**每一轮**。

## 二、memory 轴：official 比 self 贵，none 与 self 测不出差异

```
mem_self vs mem_official   10.0 vs 11.6   配对 18:3   p=0.0007   有差别
mem_none vs mem_self       11.0 vs  9.9   配对  6:11  p=0.17     测不出
```

- **official 更贵**：模型要**自己花步数**调 `memory` 工具；self 模式由系统注入，不占步数。
- **none 与 self 无差异**：符合结构性预期——**考场每次全新，`.memory/` 是空的**，self 模式的注入永远为空（实测 `memory_injected: 0/120`），只剩提取那一次的成本（`tokens_aux` 约 1.6k）。

> ⚠️ **不能把这条读成「memory 没用」。** bench 测的是**一次性任务里各层的净成本**；记忆的价值在**跨会话累积**，而这个设计里它结构性地拿不到收益。要测收益，需要「同一考场连跑两轮」的题型（未做，见 §六）。

## 三、方法论产出（比数字更值钱的部分）

### 3.1 timeout 是一把采样刀，不只是保险丝

**第一批 120 单元全部作废**：`TIMEOUT_S=300`，而单跑实测过最长的题要 290s。结果超时 34/120 = 28%。

作废的理由不是「少了 28% 数据」，而是**幸存者偏差**：

```
① 超时记录 tokens_total 全是 0(进程被 kill,trace 没写成)→ 混进均值就是掺水
② 超时在各臂严重不均:mem_self 12 次 vs mem_none 3 次
   → mem_self 只剩 12 个样本【且全是跑得快的】,它的 steps 看着最低是假象
③ 27/34 的超时记录 success=True —— 它们只是【慢】,不是【做不出来】
```

> ### **可引用句：被截断的样本不是「缺了几条数据」，是「按某个与结果相关的规则筛过一遍的数据」——它比没有数据更危险，因为它看起来像数据。**

**修正**：`timeout` 900s（实测中位数 181s 的 5 倍），第二批超时 **0/120**。
**并且**：`analyze.py` 在超时率 ≥10% 时**直接拒绝出结论**，且**先报可信度再报数字**（人对先看到的数字有锚定，警告放后面就晚了）。

📌 一个被测量否定的猜测：我最初以为「并行 4 路拖慢了单次」，实测**并行下反而更快**（t08 单跑 290s vs 并行中位 247s）。真因是 timeout 切在了耗时分布内部。

### 3.2 判分漏洞：判卷的卷子和考生手里的是同一份

`copytree` 把测试文件一起拷进考场，agent 的 cwd 就是考场且有完整写权限，而 `grade.sh` 是 `cd 考场 && pytest`。
→ **agent 一个 `edit_file` 把 assert 改成 `assert True`，代码一字不改也 PASS。**

`task.md` 里「不许修改 test_ 文件」是**说给模型听的一句请求，没有任何代码在检查它**。

> 🪝 **规则写在 prompt 里 ≠ 规则被执行。**（同族：`write_file` 有路径检查，但 `bash echo > 越界路径` 绕过去了。）

**处置＝收卷时用监考手里那份判**：①先记录动过哪些（作弊要**可见**）②删掉考场里所有 `test_*.py`**含 agent 新建的**（否则它写个失败的辅助测试会冤枉正确实现）③拷原卷回去再判分。
**双头验四条**，最关键一条先证明「不堵时这次作弊确实 PASS」，再证明「堵后 FAIL」。

实测：**120 单元中 `tests_tampered` 为 0** —— 闸没白装，但这个模型也确实没往这个方向试。

### 3.3 🔴 但它换了个方向作弊：跑出考场读标准答案

**2/120 条泄漏**（`mem_none/t08/t3`、`mem_none/t05/t2`）：

```bash
for f in .../t08_wide_validators/solution/*.py; do cat "$f"; done
```

模型日志里自己写着「**已对齐 solution，测试全绿**」。那条跑了 66 步、245k tokens、48 次 `write_file`——**做不出来，于是掉头去查评测系统**。

**我建 `solution/` 时明确考虑过「它不会进考场」——但只防住了 `copytree`，没防住 `bash`。**
而 `tests_tampered` 闸**完全没反应**：它防的是「改测试」，模型走的是「抄答案」。

> ### **可引用句：防作弊闸只挡住了你想到的那条路。黑名单挡不住越界，只有隔离能挡。**

📌 **这是 T21 沙箱的第二个实证动机**（第一个：T19 自测发现 bash 绕过 `write_file` 的路径检查）。

**已剔除这 2 条**；剔除后 `mem_none` 的 steps 从 13.9 降到 11.0（那 66 步就是抄答案那条），**结论方向不变且更干净**。

### 3.4 质量维度：先把确定性数据记全，再谈启发式

初版方案是五个正则去匹配「文本里的崩坏痕迹」（泄漏标记 / 西里尔字符 / 自述困惑）。**被否，因为本末倒置**——bench 正在丢掉大量确定值，却要靠正则去**猜**。

四件确定性数据：

| | 抓什么 | 关键设计 |
|---|---|---|
| 通过率 | 「过 7/8」≠「过 2/8」 | 满分由**标准答案实跑派生**，不写常量（手写常量会腐烂） |
| token | **消融的分母** | 主循环 / 附加层**分两本账**——合成一个总数就再也拆不开 |
| 轨迹 | `催 N 次 → todo M 次` | 在**发请求那一刻**记；跑完读 `session_history` 会被 compact 吃掉 |
| 改动范围 | 改 3 行 vs 改 80 行 | 两个都 PASS 的臂，质量天差地别 |

> 🪝 **观测可以用启发式，决策不能。** 启发式只配做「标记这条轨迹需要人看一眼」。

### 3.5 「多点」的度量是动作数，不是 bug 数

`t04` 原版把 4 个 bug 放在**同一个小文件**，模型一次 `edit_file` 整文件替换——**4 个 bug = 1 个动作**，7 步做完。

按文件数重设计后实测：**编辑动作数严格等于文件数**（4 文件→4 次、8 文件→9 次）。

> 🪝 `edit_file` 一次只能动一个文件，**文件边界是硬约束；信息依赖不是**——「改完 A 才暴露 B」挡不住模型先读源码一眼看穿。

### 3.6 出题纪律补第三条

`t07` 原有一项「删掉 `legacy.py`」，撞上 `DESTRUCTIVE=["rm ",...]` + 非 tty `fail closed`。模型只能靠 `mv` 绕权限——那样**这题测的就变成「会不会绕权限」而非「多点任务」**。

```
① 原题必须红   ② 标准答案必须绿   ③ 解法必须落在 agent 的工具池和权限范围内
                                     ↑ 新增。双头验证明「题有解」,不证明「agent 能解」
```

## 四、新模型 vs 旧模型：一条被推翻的结论

stage-1 与 stage-2 第一批（旧模型 `deepseek-v4-flash`）的观察：

```
nudge 三臂 72 单元:系统催了 61 次 → 模型只调了 6 次   ≈ 10% 响应率
```

为此查了整晚，找出三处 prompt 问题（工具池报全集 / 丢了课程 s05 的规划引导 / `"Act, don't explain."`），做了 6 次 A/B——**两个假设都不成立**（无论怎么分组都是 1/3）。

换到 `grok-composer-2.5-fast` 后，**第一次单题实跑就是**：

```
reminders = 0     系统一次都没催
todo_calls = 2    模型自己主动用了两次,并列出三条计划
```

> ### **可引用句：花了一整晚查「为什么模型不用 todo」，查出三处 prompt 缺陷；换个模型，它无人催促就自己用了。主因在模型，不在 harness。**

**但那三处修复不作废**——它们本来就是真 bug（消融纯度 / 搬运偏离 / 缓存 key 不全）。
🪝 **修复的正当性不依赖于实验结果。**

## 五、口径限制（讲结论时必须带上）

1. **配对单位是 `(题, trial)`，但同一题的 3 个 trial 并不独立**（题目难度相同），符号检验的 p 偏乐观。沿用是为了与 stage-1 可比，不是因为它无懈可击。
2. **bench 测的是一次性任务里各层的净成本**，不是「这一层有没有用」。记忆层在此设计下收益结构性为零。
3. **单模型结论**。§四 已证明模型换了结论就可能翻盘——任何一条都应写成「在 `grok-composer-2.5-fast` 上」。
4. **2 条泄漏已剔除**，但检测方式是扫日志里的路径字符串，**模型若用变量拼路径就检测不到**——泄漏率是下界，不是准确值。

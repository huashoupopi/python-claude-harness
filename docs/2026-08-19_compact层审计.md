## 1. 五个机制

主循环每轮进 API **之前**的实际顺序是四步，不是指令包里写的三步：

```
3700  messages[:] = tool_result_budget(messages)  # 内部才调 persist_large_output
3701  messages[:] = snip_compact(messages)         # L1
3702  messages[:] = micro_compact(messages)        # L2
3703  try_compact(messages)                        # L4  proactive
```

指令包 08-19 记的是 3644–3646 三行（L1/L2/L4）。那是加 A1/A2 之前的行号，而且漏了同一段里的 L3。以代码为准。

另两条不走上面这个门槛：`try_compact(..., force=True)`（模型调 compact 工具）、`reactive_compact`（API 报上下文超长）。

### 1.1 persist_large_output（经 tool_result_budget）

| | |
|---|---|
| 定义 | `persist_large_output` :720；调用方 `tool_result_budget` :730 |
| 主循环调用点 | :3700，每轮 API 前 |
| 触发 | ① 最后一条必须是 tool 消息，否则整段直接 return ② 全部 tool 消息的 `content` 长度合计 `> 200_000` ③ 从最长的开始，只处理单条 `> PERSIST_THRESHOLD`（30000）的 |
| 阈值 | `PERSIST_THRESHOLD = 30000`（:78）；预算 `max_bytes=200_000`（:730 默认参数） |
| 丢掉什么 | 单条 tool `content` 换成占位符：路径 + 前 2000 字符预览。原文写到 `.task_outputs/tool-results/{tc_id}.txt`，已存在则不覆盖 |
| 不会丢 | 非 tool 消息；最后一条不是 tool 时**整层不跑**；单条 ≤30000 的 tool 结果即使合计已经很大也不会被落盘 |

注释 :832 写「persist_large_output 在 30000 就把大输出落盘」。代码路径不是这样：30000 只是预算超标之后的**单条门槛**，单条 30001 但合计 ≤200000 时这一层不动。

### 1.2 snip_compact（L1）

|---|---|
| 定义 | :674 |
| 主循环调用点 | :3701 |
| 触发 | `len(msgs) > max_msgs`，默认 `max_msgs=50` |

## 2. 实测：L4 在什么情况下才会触发

方法：造递增长度的假 messages，按主干顺序跑，打印每层前后 `len(str(msgs))`。`summarize_history` 换成 stub，只记「L4 有没有进 compact_history」。

### 2.1 短 tool 结果（200 字符）—— 条数再多 L4 也不响

| pairs | 条数 | before | L3 | L1 | L2 | L4 响了吗 |
|---:|---:|---:|---:|---:|---:|---|
| 10 | 22 | 4070 | 4070 | 4070 | 2817 | 否 |
| 24 | 50 | 9698 | 9698 | 9698 | 5939 | 否 |
| 40 | 82 | 16130 | 16130 | 10172 | 6234 | 否 |
| 80 | 162 | 32210 | 32210 | 10173 | 6235 | 否 |
| 120 | 242 | 48330 | 48330 | 10213 | 6275 | 否 |

L1 把条数钉在 ~53 之后，L2 再把旧结果抹成 21 字符，出口稳定在 ~6200。距离 500000 差两个数量级。

### 2.2 中等 tool 结果（20000，低于 persist 30000）—— L1 能把 size 送到门槛边上，L2 再按下去

| pairs | before | L3 | L1 | L2 | L4 响了吗 |
|---:|---:|---:|---:|---:|---|
| 10 | 202070 | 202070 | 202070 | 62217 | 否 |
| 24 | 484898 | 484898 | 484898 | 65339 | 否 |
| 40 | **808130** | 808130 | **505172** | 65634 | **否** |
| 80 | 1616210 | 1616210 | 505173 | 65635 | 否 |

`pairs=40, result=20000` 是这次最关键的一行：

- L3 不动（单条 20000 < 30000，不落盘）
- L1 裁完还剩 **505172 > 500000**
- L2 接着把旧结果抹掉，掉到 65634
- L4 看到的是 65634，不响

也就是说：**L1 已经把历史送到门槛之上，L2 在 L4 检查之前把它按回去了。** 若没有 L2，这一组 L4 会响。

### 2.3 大 tool 结果（50000，高于 persist 30000）—— L3 先把合计压到 200k 附近

| pairs | before | L3 | L1 | L2 | L4 响了吗 |
|---:|---:|---:|---:|---:|---|
| 5 | 251070 | 155292 | 155292 | 55334 | 否 |
| 10 | 502070 | 166847 | 166847 | 8550 | 否 |
| 24 | 1204898 | 199243 | 199243 | 11675 | 否 |
| 40 | 2008130 | 188378 | 105860 | 11970 | 否 |

L3 在这里起了作用：合计超过 200000 且单条 >30000，大结果被换成占位符。之后 L1/L2 继续往下压。L4 全程不响。

### 2.4 跳过 L3，只跑指令包点名的 L1→L2→L4

| 条件 | before | L1 | L2 | L4 响了吗 |
|---|---:|---:|---:|---|
| 40 pairs × 200 | 16130 | 10172 | 6234 | 否 |
| 40 pairs × 20000 | 808130 | **505172** | 65634 | **否** |
| 40 pairs × 50000 | 2008130 | 1255172 | 155634 | 否 |
| 80 pairs × 20000 | 1616210 | 505173 | 65635 | 否 |

没有 L3 时，`40 pairs × 50000` 的 L1 出口是 125 万字符，L2 仍能收到 155634（<500000）。**只要历史的体积主要在旧 tool 结果上，L2 单独就能让 L4 看不到超标。**

### 2.5 纯文本、没有 tool —— L2/L3 帮不上，L4 会响

| 条件 | 条数 | before / L1 / L2（三层相同） | L4 |
|---|---:|---:|---|
| 10 轮 × 1000 字 | 22 | 20780 | 否 |
| 24 轮 × 1000 字 | 50 | 49774 | 否 |
| 24 轮 × 12000 字 | 50 | **577774** | **响** → 事后 size=115、2 条 |
| 24 轮 × 20000 字 | 50 | 961774 | **响** |
| 5 轮 × 80000 字 | 12 | 800425 | **响** |
| 10 轮 × 80000 字 | 22 | 1600780 | **响** |

L1 条数不到 50 就不裁。L2 不碰非 tool。所以「少量超长 user/assistant 正文」是这条 proactive 路径实测会走通的形状。

### 2.6 L1 裁到 ~51 条之后，每条多长才会在 L2 之后仍超过 500000

材料：60 轮纯文本（122 条），L1 裁到 51 条。

| 每条 content | L1/L2 后 size | L4 |
|---:|---:|---|
| 100 | 6628 | 否 |
| 1000 | 49828 | 否 |
| 5000 | 241828 | 否 |
| 8000 | 385828 | 否 |
| 10000 | 481828 | 否 |
| 12000 | **577828** | **响** |

在「L1 已经打到条数上限、且没有可抹的 tool 结果」时，留下来的消息平均大约要到 **1.2 万字符** 这一档，L4 才会响。1 万字符那档是 481828，还在门槛下。

### 2.7 贴近今天 10 单元 bench 的规模

假历史：6 对、result=400（对应今天 `run_20260819_194107` 平均约 9.4 步 / 5–6 turn）。

| | size | 条数 |
|---|---:|---:|
| before | 3670 | 14 |
| L3/L1 | 3670 | 14 |
| L2 | 2533 | 14 |
| L4 | 不响 | 14 |

同批 10 单元 `ctx_chars_max`（bench 探针：只加 `content` 长度，比 `len(str(msgs))` 更小）：最大 5216，均值 3144.7。和 500000 比，差两个数量级。

## 3. 冲突点（只陈述，不处置）

1. **L2 挡在 L4 前面，吃掉 L1 刚送过线的体积。**  
   `40 pairs × 20000`：L1 后 505172 > 500000，L2 后 65634，L4 不响。proactive 摘要看到的是 L2 之后的世界。

2. **L3 和 L2 抢同一批旧 tool 结果。**  
   单条 >30000 且合计 >200000 时，L3 先把大结果换成落盘占位符；L2 再把「超过 3 条的旧结果」换成 21 字符。两条都会改 tool `content`。L3 只在最后一条是 tool 时才开工。

3. **L1 只管条数，不管体积。**  
   50 条以内，单条 8 万字符也过 L1。L2 也不碰非 tool。这种形状会直接到 L4（实验 2.5）。tool 结果占体积的形状走不到这里。

4. **L3 的真实开关不是「单条 >30000」。**  
   代码要先满足「最后一条是 tool」和「全部 tool content 合计 >200000」。注释 :832 写成「30000 就落盘」，和代码不一致。以代码为准。

5. **同一轮里 L3 可能根本没跑。**  
   回合以 user / reminder / assistant 结尾时，`tool_result_budget` 第一行就 return。L1/L2/L4 仍会跑。

6. **两条摘要路径门槛不同。**  
   proactive：看 `len(str(msgs)) > 500000`。  
   reactive：看 API 是否报超长，不看 500000。  
   模型调 compact：`force=True`，也不看 500000。  
   所以「自动摘要是不是死代码」要拆开问：proactive 那条、reactive 那条、工具那条，不是一件事。

7. **`estimate_size` 和 bench 的 `ctx_chars_max` 不是同一个尺子。**  
   前者 `len(str(msgs))`（含 role、key、引号、tool_calls 结构）；后者只加 `content`。对比 500000 时只能用前者。

8. **micro_compact 原地改对象。**  
   `snip_compact` 返回的新列表里仍是原消息对象。L2 改 content 会写回这些对象。本报告每组都是 deepcopy 后测的，数字不受上一组污染。

## 4. 对「自动摘要是不是死代码」的实测回答

问的是 proactive `try_compact`（`force=False`，看 500000 那条）。

- **在 tool 结果占体积的历史上：这组测量里 proactive L4 一次都没响。** 即使 L1 已经把 size 送到 505172（过线），L2 也会在检查前把它按回 6 万左右。旧 tool 结果再多，出口也被钉在「3 条近期全文 + 一堆 21 字符占位符 + 最多约 50 条」。
- **在非 tool 的超长正文上：会响。** 50 条、每条约 1.2 万字符；或十几条、每条 8 万字符。这是这次唯一测到 `fired=True` 的形状。
- **在今天这类 bench 任务上：响不了。** 10 单元 `ctx_chars_max` 最大 5216；仿 6 轮假历史 `len(str(msgs))` 约 2500–3700。离 500000 差两个数量级。

reactive 和 `force=True` 没走 500000，这次没测它们在真实 API 错误上的频率。
